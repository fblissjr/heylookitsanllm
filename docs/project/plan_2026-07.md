## Direction -- why this plan exists

Sole-user hobbyist project. The grounding below was verified against primary
sources in July 2026 (inlined here so this stays self-contained):

- **MLX is healthy post-Awni.** Awni Hannun left Apple 2026-02-27 (now at
  Anthropic), but the core team stayed (Katharopoulos, Digani, Zhao, Collobert)
  and keeps cutting mlx-lm releases with a healthy community-PR flow -- MLX no
  longer depends on any individual.
- **The bet is baked into Apple's hardware + OS**, not a research project: M5
  Neural Accelerators are co-designed for MLX (~4x TTFT vs M4 -- though that gain
  does NOT reach the M2 Ultra this runs on); WWDC26 made MLX first-class in the
  Foundation Models framework (`MLXLanguageModel`); Ollama switched its
  Apple-Silicon engine off llama.cpp onto MLX (2026-03), NVIDIA contributing
  quantization + CUDA work.
- **No pivot to gguf/llama.cpp.** MLX wins steady-state decode (1.4-1.8x, up to
  3x on MoE) and memory (7-13%); llama.cpp still wins short-prompt prefill/TTFT,
  30K+ long-context decode, and architecture breadth -- none reverse the bet, and
  the radix prompt cache directly attacks MLX's one real weakness (repeated-prefix
  prefill). On the M2 Ultra the edge is memory architecture + decode speed, not
  the new silicon.
- **Verification-based decoding is a real wave, not flavor-of-the-month.** DFlash
  (z-lab, Feb 2026: a tiny block-diffusion drafter predicts ~16 tokens/forward,
  target verifies in one pass, lossless; native port `dflash-mlx` reports ~4x on
  Qwen3.5-9B at 89% acceptance) and DSpark (DeepSeek+PKU, Jun 2026: 60-85% faster,
  byte-identical, ships a draft-training repo) -- a ships-with-draft-head artifact
  is becoming as normal as "comes in 4-bit."
- **mlx-vlm is the stack's top bus-factor risk** (one maintainer) but alive and
  accelerating; LM Studio's unified mlx-engine independently formalized our
  pre-filled-cache split (mlx-lm always generates; mlx-vlm demoted to a vision
  add-on), Apple's official VLMs are Swift-only (mlx-swift-lm), and mlx-lm #993
  tracks Python multimodal.

Load-bearing conclusions:

- **The MLX bet holds; don't pivot.** Post-Awni MLX is healthier (M5
  co-design, WWDC-2026 Foundation Models, Ollama switched to MLX). Ride
  mlx-lm/mlx-vlm with minimal custom code.
- **Ecosystem posture (2026-07-06, full briefing:
  docs/architecture/ecosystem_strategy.md -- READ before perf
  or provider work):** the Python MLX stack is the right rail but is
  maintenance-mode infrastructure, not a living upstream (mlx-lm
  release-starved: 20+ unreleased commits, 259 open PRs, HF quietly
  co-maintaining; Apple's feature frontier ships in mlx-swift-lm).
  Operating rules: SHA-pin rather than wait for PyPI releases; check the
  open-PR backlog BEFORE writing any workaround; expect new capabilities
  (spec decoding especially) via sidecar packages like dflash-mlx, never
  via an mlx-lm release. Invariant to protect above all:
  `run_generation()` as the single chokepoint + the provider seam in
  config.py -- it converts ecosystem risk into a config entry (DFlash
  sidecar / Swift shim / llama-server all register as providers). The
  doc carries the tripwires (next mlx core wheel = load-bearing signal;
  day-one support location for the next frontier model = diagnostic) and
  the alternatives-considered so Swift/llama.cpp/fork isn't relitigated
  per session. Its perf ordering matches Phase 5: measurement first,
  then draft-model spec decode, then prefix-cache hit-rate, then
  memory-budget admission/batched decode; VLM pre-filled-cache path is
  incompatible with radix AND speculative prefill -- vision perf lives
  in the feature cache, not decode tricks.
- **Identity: an inference SCHEDULER for one machine with many demanding
  clients** (ComfyUI captioning, scripts, v3 frontend, agents) -- not an
  OpenAI-compatible endpoint (commodity). Differentiators: prefix cache,
  router/pinning/idle-unload, admission + batching, observability. Invest
  there.
- **Next capability wave: verification-based decoding** (DFlash/DSpark;
  lossless 3-4x decode). Our single chokepoint
  (`generation_core.run_generation` -> `stream_generate`) makes adoption a
  provider-internal change. Dormant `draft_model_path` is the on-ramp:
  classic speculative baseline FIRST, DFlash decision at week 4.
- **mlx-vlm bus factor (one maintainer) -- strategy adopted 2026-07-06:**
  LM Studio's unified mlx-engine formalized exactly our pre-filled-cache
  split (mlx-lm always generates; mlx-vlm demoted to vision add-on) -- our
  architecture is the ecosystem answer. Apple's official VLMs are
  Swift-only (mlx-swift-lm); mlx-lm #993 tracks Python multimodal. Either
  resolution is fine if the dependency is shaped right:
  1. **Contract tests** (Phase 1 item below): transcribe the 07-06 drift
     audit into tests/contract/test_mlxvlm_surface.py pinning the consumed
     surface (prepare_inputs 4-tuple, apply_chat_template kwargs,
     encode_image, LanguageModelOutput fields, _position_ids/_rope_deltas)
     plus mlx-lm private-API touchpoints (_get_classes, cache classes,
     GenerationResponse fields). Transcription, not research.
  2. **Shrink mlx-vlm per-model, need-driven**: when a new VLM's language
     tower is an arch mlx-lm implements, drive it with mlx-lm's text
     implementation (kills the wrap_language_model/position-reset bug
     class). Not speculative work.
  3. **Upstream postmortems as influence** (mlx-vlm issues + our use case
     on #993); pairs with the planned CompilerCache bug report.
  4. **Two-paragraph contingency doc**: VLM archs we run + per-arch escape
     hatch (vendor the model file / wait for mlx-lm / llama-server). Worst
     case is annoying, not existential.
  Anti-actions: no fork, no preemptive vendoring, no upgrade freezes --
  contract tests make aggressive upgrading safe.
- **Swift rewrite: NO (decided 2026-07-06).** Value is orchestration, not
  compute; Python is MLX's first-party ships-first rail; the real asset is
  encoded correctness knowledge (becoming executable via contract tests).
  Ollama's Go-wrapper lesson = keep the hot loop inside the framework,
  which stream_generate already does. Tripwires that reopen it (likelihood
  order): (1) Apple privileges the Swift rail -- watch mlx-swift-lm vs
  mlx-lm release notes (same watch as the mlx-vlm strategy), trust notes
  not vibes; (2) token loop MEASURED Python-bound at 300-400+ tok/s --
  only meaningful after the Phase 1 telemetry fixes; fixes 1-3 are batch
  the loop / MLX-op hot paths / chunked emission, rewrite is fix 4;
  (3) product shape changes to a distributable Mac app (a new project, not
  a rewrite); (4) Python-binding rot (least likely). Standing hedge:
  BaseProvider's now-crisp contract (typed exceptions, check_capacity,
  queue stats) means a Swift sidecar registers as just another provider --
  a config entry, not a bet-the-project decision.
- **Frontend discipline**: the introspection pages (Token Explorer,
  Notebook) are the defensible UI. Do NOT rebuild chat a fourth time.
- **Shrink before you grow**: deletions (v2, dead surface, config_tui)
  precede the exciting work; every deleted line cheapens the
  scheduler/decoding work. The reverse is false.

  verification-based-decoding experiment the perf track will run.
- Native mlx-lm prompt_tps/generation_tps: never read. /v1/messages

## Phase 6 -- model-management redesign (SPLIT 2026-07-28: 6a = Wave 1 derive-at-load substrate, NOW; 6b = Wave 4 admin surface, after Waves 2-3)

New 2026-07-10 (owner-raised while scoping the j-space lens work). A captured
DIRECTION, not a build plan -- shape it into phased items in a later re-plan
pass. Coupled to the j-space work because lens management lands on the same
admin surface (see the j-space plan + `docs/frontend_v3.md`).

**Problem (grounded in the code, not vibes).** `models.toml` is brittle as an
interface:

1. **Scan regenerates, doesn't merge.** `model_importer.py` (525 lines) scans
   dirs + the HF cache and HAND-BUILDS toml text (`_model_to_toml_lines` ->
   `generate_toml` -> `f.write`), so a re-scan can clobber hand-edits.
   `admin_api.py` (453 lines) also writes the file.
2. **Identity is id-only.** `already_configured` matches by id, never resolved
   `model_path` (Phase 1 item 8) -- re-import is skip-not-update and path
   collisions aren't caught.
3. **No non-toml path to add/edit/enable a model.** It's hand-edit-the-toml or
   the CLI import -- both high-friction; hand-editing toml is the owner's
   stated pain point.

Note the file already bakes an absolute `model_path` per entry, so "point at a
model in any folder" is technically supported today -- the friction is in
GETTING an entry in/out, not in path flexibility.

**Direction.**

1. **Registry-over-scan: structured, non-clobbering.** Treat `models.toml` as
   generated-plus-overrides. A structured writer (tomlkit -- preserves
   comments/formatting) that MERGES by resolved `model_path`, never blind-
   regenerates. User overrides live in a layer a re-scan cannot stomp.
2. **"Point at a path, anywhere" as the primary add flow.** Add-by-path (file
   or dir, any location) -> sniff (reuse the `_is_mlx_model` /
   `_is_vision_model` / `_read_model_config` introspection) -> propose an entry
   -> confirm. No required folder convention.
3. **The v3 admin/model-management page is the real UI.** The `models` page
   already consumes `/v1/admin/models` + `/import` + `/scan` + load/unload;
   promote it from list+load/unload to full CRUD: add-by-path, edit
   id/tags/config, enable/disable, dedupe, re-scan-as-merge -- so the toml is
   an implementation detail, not the interface. Coupling recorded in
   `docs/frontend_v3.md`.
4. **Lens management lands on the same surface -- but fitting runs OUT of the
   server.** A fitted/converted j-space lens is another per-model artifact
   (`adapters/jspace/<model_id>/`); "which models have a lens", convert+register,
   and *triggering* a fit belong next to the model CRUD. But lens **fitting itself
   lives in the `jlens-mlx` sibling repo** (same lean-scheduler reasoning as Q6's
   `rlm-heylook` extraction -- this server only *applies* lenses; see the j-space
   plan Part 2). The admin surface manages/triggers fits as out-of-server jobs; it
   does not host the fitting pipeline. This coupling is what surfaced the redesign.

**Guardrails (do not regress).**

- `models.toml` still validates strictly (`extra="forbid"`, config.py) -- the
  structured writer emits only known fields; the invariant stays.
- Keep `model_path`-anywhere; never introduce a required directory layout.
- Sole-user hobbyist scope: stay lightweight. A structured merge + an admin
  CRUD page, NOT a model database or a package manager.

**Seeds already in the plan:** Phase 1 item 8 (import/re-import path identity +
PUT semantics) is the correctness prerequisite; Phase 2 item 5 (config_tui
retire) removes the drift-prone hand-editing helper this replaces.

**Refinement 2026-07-11 -- modality/loader split (decided; data model lands
ahead of the substrate).** Surfaced by a j-space crash on the Qwen3.5 VLM: a
`vision = true` model auto-routes to the mlx-vlm engine, whose hybrid attention
assumed a non-None cache (fixed at capture.py; see CHANGELOG 1.34.42). Root
smell: `vision: bool` (MLXModelConfig) does TWO jobs -- *describes* the model
(has a vision tower) AND *selects the loader* (mlx-vlm vs mlx-lm) -- which is why
a model like Qwen3.5 (a true VLM you may prefer to run text-only via mlx-lm) had
no clean representation. Decision -- split them, staying inside the guardrail
(strict TOML, NOT a DB):

- `modalities: list[str]` -- DESCRIPTION, detected from the config's own blocks
  (`vision_config`/`audio_config`/`text_config` + `*_token_id` keys are the
  model author's ground truth; filenames/preprocessor are fallback for sparse
  GGUF/split checkpoints). Represents genuinely multi-modal models (gemma-4
  declares text+vision+audio) that a single bool cannot.
- `loader: "auto" | "mlx-vlm" | "mlx-lm"` -- ROUTING, within `provider="mlx"`
  only. `auto` := mlx-vlm if `"vision" in modalities` AND mlx-vlm registers the
  `model_type` (`mlx_vlm.utils.get_model_and_args`), else mlx-lm. Both new
  fields live on `MLXModelConfig`, so `loader="mlx_embedding"` is unexpressible
  by construction (embedding entries use the other Union arm).
- Back-compat: absent `modalities` => `["text","vision"] if vision else
  ["text"]`; `is_vlm` derives from the effective loader. Existing toml entries
  and the provider are unchanged.

Engine-path hierarchy (for observability's `dim_model`): `provider`
(mlx | mlx_embedding) sits ABOVE `loader`; the three paths are mlx_embedding,
mlx+mlx-vlm, mlx+mlx-lm. `dim_model` carries `provider` + `modalities` +
`loader` (configured) + `effective_loader`/`is_vlm` (resolved). Invariant:
model capability (a `dim_model` attribute) stays distinct from request content
(`fact_request.image_count`) -- "VLM served a text request" is the join, not a
collapsed field.

Sequencing (coordinated with the observability/config work): the DATA MODEL
lands first (schema + detection + derivation on `MLXModelConfig`; no persistence
rewrite) so telemetry and the eventual CRUD build on a stable contract. `loader`
is RESERVED now (default `auto`, routing branch honored); a *durable, hand-set*
`loader` override waits for the tomlkit non-clobbering merge above (a re-scan
still regenerates today, so a manual override isn't durable until then --
Option 2, not a lone bolted-on field). Operational settings (observability
level/retention, `max_loaded_models`, `idle_unload`) are NOT the registry and
go to an App-DB `settings` table -- outside this guardrail.

Two more entry classes the redesign must account for (raised 2026-07-11; note
now, design in the substrate pass):

- **Entry KIND is under-modeled, like vision was.** `provider`
  (mlx | mlx_embedding) doesn't capture that some `provider="mlx"` entries are
  NOT servable chat models -- e.g. `gemma-4-26B-A4B-it-assistant-bf16-mlx` is an
  MTP/draft head ("no chat template on purpose"), flagged only by a `draft` tag
  + description. The kinds are: chat model, draft/MTP head, embedding. The
  modality/loader fields apply to servable chat models; a draft-head entry
  should carry a `kind` (or role) so the UI/capabilities/telemetry don't treat
  it as a chat model, and `detect_modalities` shouldn't over-claim for it. NB
  detection must stay robust for these (odd/absent config.json blocks ->
  default `["text"]`, never crash).
- **Per-model SIDECAR ARTIFACTS are a managed class.** A model entry can own
  out-of-band artifacts: a draft model (`draft_model_path`), a j-space lens
  (`adapters/jspace/<model_id>/`, git-tracked dir + gitignored contents), and
  plausibly LoRA adapters later (`adapters/...`). Phase 6 item 4 already lands
  lens management on the admin surface; generalize it -- the CRUD surface
  manages a model's sidecars (draft, lens, adapters) as a coherent group, not
  one-off. `HEYLOOK_JSPACE_DIR` defaults under `adapters/`.

**Refinement 2026-07-28 -- derive-at-load, override-only registry (decided;
reshapes item 1).** Surfaced by the gemma thinking-loop fix (v1.45.0/1.46.0):
the loop's root cause was a *server-side copy of derivable truth going stale*
(hardcoded sampling floor standing in for each model's own
`generation_config.json`; a cascade layer keyed on a config field nothing
writes). The fix -- read vendor truth at use-time, key behavior on effective
state -- generalizes to the registry itself and SIMPLIFIES item 1:

- **models.toml conflates three things**: (a) a catalog of what exists
  (derivable by scan), (b) derived metadata materialized at import --
  `modalities`, `chat_template_source` (the auto case), `description`/`tags`
  auto-text, cache/kv smart defaults, and formerly sampler fields -- which
  rots when a model dir changes in place, and (c) operator INTENT (enabled,
  loader override, measured spec-decode opt-ins, ctx/max_tokens caps,
  default_sampler, gguf server plumbing). Only (c) needs to be authored.
- **Direction shift**: instead of building tomlkit merge machinery so
  re-scans preserve derived fields (item 1 as originally written), STOP
  MATERIALIZING derived fields -- resolve them at load the way the vendor
  sampling layer (samplers.load_vendor_sampling, v1.45.0), template
  auto-resolution (template_info.py), and the capability template probe
  already do. Data never written can't be clobbered and can't rot. Merge
  machinery is then only needed for the small intent layer -- and may prove
  unnecessary if entries shrink to `id + model_path + provider + overrides`.
- **Precedents now in tree**: vendor sampling layer (v1.45.0); ONE shared
  cascade `samplers.resolve_effective_sampling` for both providers
  (v1.46.0); `vision` as a derived mirror (2026-07-11); MLX
  `supports_thinking` REMOVED v1.46.0 (was a manual flag triple-shadowed by
  derivable truth -- the same rot class; GGUF keeps its flag because GGUF
  metadata has no cheap pre-load probe).
- **Derive-at-load candidates for the substrate pass**: `modalities`
  (detect_modalities already reads config.json -- run it at load, store only
  explicit overrides), `chat_template_source` auto (store only explicit),
  description/tags auto-text (generate for display, don't store),
  cache/kv smart defaults (compute at load from weight size + machine),
  context budgets (config.json `max_position_embeddings` / GGUF metadata --
  needs prompt-length-aware max_tokens logic, design before building).
- Guardrails unchanged: strict TOML validation, `model_path`-anywhere, no
  DB, sole-user lightweight scope.
